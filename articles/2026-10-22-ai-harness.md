## はじめに

Claude Code を毎日使っていて、CLAUDE.md (毎回の会話の最初に読ませる指示ファイル) に決まりを書き足したり、skill (要るときだけ読ませる手順書) をいくつも作ったり、危ない編集を hook (決まった瞬間に必ず動く script) で止めたりしてきた。それなのに、改まって「ハーネスとは何か」と聞かれたとき、答えられない。coding agent の話でよく見る言葉ではあったが、いざ説明しようとすると、何を指すのかあやふやな部分が多かった。

これを機会に調べ直そうと思い、自分用のメモも兼ねてざっくりまとめる。同じ話を、約 16 分の解説動画にもした。

https://www.youtube.com/watch?v=LLLvjJnGtnU

:::message
2026-10-22 時点の情報。動きの速い分野なので、製品の機能や数字は数か月で変わるかも。
:::

## TL;DR

- ハーネスは、coding agent が動いている間に**モデルの外で働くもの全部**。ループ・道具・文脈・制御の 4 つの箱がある
- 良くするとは、失敗のたびに「文章でお願いする・見張る・仕組みで起きなくする」の**どの段で塞ぐかを選んで、仕組みにすること**。試して確かめ、要らなくなったら外す
- 同じモデルのまま成功率や人の手間は変わる。ただし悪くなることもあって、**良くなったかは測らないと分からない**
- 自分が CLAUDE.md や hook を育ててきた作業は、まさにハーネスを良くする作業だった

## ハーネスとは

harness は、もともと馬具を指す英語。馬は力があるけど、引き綱や手綱が無いと荷車を引いてくれない。モデルを馬に、ハーネスを馬具に見立てる比喩は、論文にもそのまま出てくる。

実際、モデル単体にできることは意外と少ない。文字の列を受け取って、続きの文字の列を返す。それだけ。ファイルを読むことも、コマンドを打つこともできない。

それでも Claude Code に「テストが落ちているので直して」と頼むと直る。モデルが「テストのファイルを読みたい」と答えると、ハーネスが実際に読んで中身を渡す。モデルが直し方を答えると、ハーネスが書き換えてテストを流す。これをテストが通るまで繰り返す。つまり、モデルが考えて、ハーネスが手足になる。「エージェント = モデル + ハーネス」は、この関係のことになる。

![モデル単体と、ハーネスに包まれた agent](/images/2026-10-22-ai-harness/02-model-vs-agent.png)

中身を大きく畳むと、ループ・道具・文脈・制御の 4 つの箱になる。CLAUDE.md や skill は、モデルが一度に読める窓 (context) に何を入れるかを決める文脈の箱。hook は、モデルの判断に任せない制御の箱。

![ハーネスの 4 つの箱と、Claude Code の機能](/images/2026-10-22-ai-harness/02-four-boxes.png)

意味はまだ割れていて、「モデル以外の全部」と広く取る人もいれば、実行のループだけを指す人もいる。Claude Code の公式ドキュメントは「Claude Code がハーネスで、Claude はその中のモデル」と端的。ここでは、使う側が足した CLAUDE.md や hook も含めて、モデルの外で働くもの全部をハーネスと呼ぶ。

ここまで整理して、ようやく腑に落ちた。CLAUDE.md に 1 行足すのも、hook を書くのも、全部この 4 つの箱のどれかに手を入れる作業だった。

## 良くするとは、どの段で塞ぐかを選ぶこと

Mitchell Hashimoto の定義は単純で、agent が間違えたら、二度と同じ間違いをしない仕組みを作る、というもの。ただ仕組みには強さの違いがあって、自分が手を入れてきたものを並べ直すと 3 つの段に分かれた。

![ハーネスへの手の入れ方の、3 つの段](/images/2026-10-22-ai-harness/03-strength-ladder.png)

1. **文章でお願いする**: CLAUDE.md や skill に書く。手軽だけど、従うかはモデル次第
2. **見張る**: hook で、問題の操作をしようとした瞬間に止め、理由と直し方を返す。モデルの判断を待たずに必ず動く
3. **仕組みで起きなくする**: 設定・lint・テストで、そもそも間違えようのない状態にする。忘れる余地が無い

上の段ほど確実だけど、作る手間がかかって、判定を誤ったときの影響も大きい。どの段で塞ぐかを、失敗の性質に合わせて選ぶことになる。自分の例を 1 つずつ。

**文章でお願いする段。** 長い回答を Web ページに書き出す道具 ([cc-pages](https://github.com/pollenjp/cc-pages)) を作っていて、どの回答をページにするかは skill に書いて判断させている。すると Claude Code は上手に抜け道を見つけてくる。ファイルに書き出して「出力しました」とだけ返す。名指しで頼んでも、除外の条件を持ち出して降りる。「図で見せる」と書いても図が出てこない。見つけるたびに 1 文ずつ足して塞ぎ、図の枚数を数で書いたら、1〜3 枚だった図が 5〜6 枚になった。その代わり、56 行だった skill は 200 行を超えた。

**見張る段。** `~/.claude/` の一部を Nix で配っていて、直接書き換えると壊れる。その注意を CLAUDE.md から、編集しようとした瞬間にだけ動く hook に移し、止めるときに正しい直し方を返すようにした。モデルが注意を忘れても必ず止まり、返した理由を読んでその場で直せる。ただ最初の版は普通のコマンドまで止めてしまい、しかも直した版の commit を、直す前の hook 自身が拒否した。自分を直す commit を自分で止めたわけで、今は hook のコメントに「安全網であって境界ではない」と書いてある。

**仕組みで起きなくする段。** commit に 1Password で署名していて、承認の画面が出るたびに Claude Code が止まる。「署名を外して」と頼むのは頼み忘れるので、Claude Code の中でだけ署名を外す設定を入れた。設定はモデルが読まなくても効くので、忘れる余地がそもそも無い。OpenAI は独自の lint のエラー文に直し方を書き込んでいて、失敗したその瞬間に agent の目に入るので確実に届く。良い種類の prompt injection、とも呼ばれているとか。

## 段のほかに効いたこと

段の選び方とは別に、効いたことが 3 つある。

1 つ目は、指示が届く時刻。英語の skill を読んだ直後の Claude Code が、英語で報告してきたことがある。CLAUDE.md は会話の最初、skill は使う直前に読まれるので、長い会話の終わりでは直前の手順書につられる。なので決まりは、つられやすい場面ごと書いた。承認したら最後まで進める決まりは、承認を求める skill を読んだ直後に hook で念を押している。何を書くかだけでなく、いつ目に入るかも設計することになる。

2 つ目は、直す前と後で同じ場面を試すこと。subagent に同じ場面を解かせて、手順書を直す前と後の振る舞いを比べている。さっきの図の枚数も、この方法で数えたもの。直したつもり、で終わらせないため。

3 つ目は、引き算。Anthropic の記事によると、Claude Sonnet 4.5 には context の限界が近づくと仕事を早めに畳む癖があって、新しい agent に引き継がせる仕組みを足していた。ところが Claude Opus 4.5 では癖がほぼ消えて、その仕組みは外せたとのこと。モデルが変わったら、何をやめられるかを問い直す。

まとめると、良くする作業は 1 つの循環になる。

![ハーネスを良くする循環](/images/2026-10-22-ai-harness/03-improve-loop.png)

## 良くすると何が良くなるか

いちばん分かりやすいのは、同じモデルのまま、ハーネスだけを変えて成績が動いた報告。LangChain は Terminal-Bench 2.0 で、モデルはそのままに system prompt や道具を変えて、解決率を 52.8% から 66.5% に上げたらしい。Terminal-Bench 2.0 の論文の表でも、同じ GPT-5 を 4 つの agent で動かすと、33.9% から 49.6% まで開いている。

![同じモデルのまま、ハーネスだけを変えた報告](/images/2026-10-22-ai-harness/04-same-model.png)

ただ自分の実感でいちばん効いたのは、人の手間だった。同じ指摘を 2 回しなくてよくなる。承認の往復が減る。間違った場所への編集が、起きる前に止まる。1 つの数字にはならないけど、毎日のことなので積み重なる。

## 盛りすぎない

とはいえ、ハーネスを良くすれば何でも解決するわけでもない。

- さっきの数字の多くは、自分の製品や主張を持つ当事者が測ったもの。Terminal-Bench の論文自身も、たいていはハーネスよりモデルの選び方が大事だと結んでいる
- 悪くなることもある。2026 年の春に Claude Code の応答が悪くなったときは、原因はモデルではなく、推論の強さの既定を下げたことなど、ハーネス側の 3 つの変更だったらしい
- [「名前負け」](https://zenn.dev/karamage/articles/4788b0b791ef2d)という声もあって、中身はテストやドキュメントといった昔からの作業だという。一方で、変わったのは技術ではなく[投資対効果](https://zenn.dev/takekazuomi/articles/take-the-reins)だ、という整理もあって、どちらももっともだと思う

新しい魔法が出てきたわけではないし、良くなったかどうかは測らないと分からない。

## おわりに

振り返ると、ハーネスを良くする作業の中身は、テストを書く・lint を整える・ドキュメントを保つ、といった昔からの良い習慣だった。変わったのは、相手が agent になったこと。agent はエラー文を読んで直し、テストが通るまで何度でもやり直すので、テストがあれば、終わったかを見た目でなく結果で決められる。だから同じ習慣に、手間をかける値打ちが変わったんだと思う。

明日からできることを挙げておく。

- `/context` や `/hooks` で、自分のハーネスに今何が入っているかを見る
- 同じ指摘を 2 回したら、どの段で塞ぐかを選んで仕組みにする
- lint やテストのエラー文に、直し方を書く
- 指示を直したら、直す前と後で同じ場面を試す
- モデルが変わったら、外せる仕組みを探す

自分も、この記事を書くまで、自分が普段やっていることがハーネスの中のどの位置付けにあるものをいじっているのか知らなかった。CLAUDE.md に 1 行足すたびに、ハーネスを少しずつ良くしていたらしい。我々の手元のハーネスに何が入っているか、一度覗いておきましょうね。
