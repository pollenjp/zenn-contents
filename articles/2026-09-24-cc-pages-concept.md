Claude Code に調べものや設計の相談をすると、ターミナルに長い回答が流れてきます。表は罫線がずれ、3 つの案を見比べるにはスクロールを行ったり来たり。図はそもそも描けません。読み終わる頃には、最初に書いてあった結論がどこにあったか分からなくなっています。

ターミナルはコマンドを打つには最高の場所ですが、長い文章を読む場所ではありません。

そこで、長い回答は Claude Code に手元の Web ページとして書き出してもらい、ターミナルには結論とリンクだけを返してもらうことにしました。そのために作った小さなツールが [cc-pages](https://github.com/pollenjp/cc-pages) です。

この記事では使い方や実装には立ち入らず、作って使いながら考えたこと、つまずいたことを書きます。

同じ内容を、約 8 分の解説動画にもしました。

https://www.youtube.com/watch?v=1j_5sBJsaoY

## ターミナルには、結論とリンクだけ

たとえば bash スクリプトの罠について調べてもらうと、ターミナルに返ってくるのはこれだけです。

```txt
- set -euo pipefail だけでは、$(...) の中の失敗で止まらない
- shopt -s inherit_errexit を足せば止まる。ただし local x=$(...) は別の罠
→ (ページへのリンク)
```

これで次の指示を出せるなら、そのままターミナルで返事を打ちます。根拠や細かい比較を見たいときだけ、リンクを開きます。

![リンクの先は、表や図で読めるページ](/images/2026-09-24-cc-pages-concept/page.png)

ページは読むための場所と割り切っていて、ブラウザから Claude Code に返事を送る機能はあえて作っていません。読んだらターミナルに戻って、続きを話すだけです。

:::message
claude.ai の Artifact でも近いことはできますが、置き場所は claude.ai の側です。仕事の内容を外に出したくない、オフラインでも読みたい、ファイルとして手元に残したい。この 3 つが欲しかったので、自分のマシンの中で完結するものを作りました。
:::

## 「結論 1 行 + リンク」は割り切りすぎだった

最初はもっと思い切っていて、ターミナルに返すのは「結論 1 行とリンク」だけにしていました。

ところが実際に使ってみると、中身の詰まった結論ほど 1 行には収まりません。無理に押し込むと、判断に要る情報がこぼれてしまいます。ページを開かないと次の一言が決められないのでは、ターミナルだけで済んでいた頃より手間が増えただけです。

いまは「箇条書き 3 行まで + リンク」に落ち着いています。判断に要る結論はターミナルに、根拠と詳細はページに。「ページには表と図を入れました」のような中身の紹介も書かせません。開けば分かることに行を使うくらいなら、結論をもう 1 つ書いてほしいからです。

## いつページにするかは、Claude Code に決めてもらう

一番悩んだのは、どの回答をページにするかでした。

全部ページにすると、「はい」の一言までページになります。毎回ブラウザを開くことになるうえ、トークンも待ち時間も余計にかかります。かといって「ページにして」と頼んだときだけにすると、今度は頼むのを忘れます。便利な仕組みも、呼び出すのを忘れたら無いのと同じです。

結局、判断は Claude Code 自身に任せることにしました。長くなる回答、表や図で見せた方が早い回答、複数の案を比べる回答はページにする。yes/no で済む確認や、ちょっとした修正の報告はページにしない。この基準を skill（Claude Code に読ませる手順書）に書いておき、回答のたびに判断してもらいます。

ページにしない場面まで書いておくのがコツです。これがないと、ちょっとした返事までページにされかねません。

## 抜け道を塞ぎながら、基準を育てる

この基準は、一度書いて終わりにはなりませんでした。自動でテストできるものではないので、使いながら「出しすぎ」「出さなすぎ」を見て文言を直していきます。やってみると、Claude Code はなかなか上手に抜け道を見つけてきます。

- **md ファイルに逃げる**: 調査結果を md ファイルに書き出し、「ファイルに出力しました」とだけ返す。ターミナルに残る出力が短いので、「長い回答ではない」と判断されてページにならない
- **名指ししても断られる**: 「ページにして」と頼んでも、「答えが 1 行ならターミナルで返します」と、ページにしない場面の条件を持ち出して降りてしまう
- **図が出てこない**: 「図や表で見せる」と書いておいても、出てくるのは文章と表ばかり。「節ごとに図を 1 枚以上」と数で書いて、ようやく図が描かれるようになった

見つけるたびに、基準へ一文ずつ足して塞いできました。最初は数行だった基準も、いまではずいぶん長くなっています。

## Claude Code に書かせるのは「中身」だけ

ページの作り方にも一工夫あります。

素直に考えると、Claude Code に HTML を丸ごと書いてもらえば済みます。ただそれだと、1 ページごとにトークンがかさみ、見た目も毎回微妙に違うものができあがります。ナビゲーションのような共通の部品を後から足すこともできません。

そこで Claude Code には本文だけを書いてもらい、配色やナビゲーション、ページの一覧は cc-pages の側で被せることにしました。書く側は中身に集中でき、見た目はいつも揃います。

Markdown で書かせるのが一番手軽ではあります。ただ、それでは「表や図で見せたい」というそもそもの動機を手放すことになるので、HTML にしました。

## 道具のせいで回答が止まったら本末転倒

ページが書けなかったときは、黙ってターミナルで普通に答えてもらいます。cc-pages の入っていないマシンで作業していても、回答は止まりません。便利にするための道具のせいで肝心の回答が返ってこないのでは、本末転倒です。

おもしろかったのは、試しに cc-pages を PATH から外したときのことです。Claude Code は作業ディレクトリにあったバイナリを自力で見つけ出して、そのまま使っていました。ちゃんと報告はしてくれるのですが、これでは止めたくても止められません。いまは「見つからないのは、わざと外してある合図。ほかの場所を探さない」と skill に書いてあります。

## ページが増えたら、今度は「いまどこ？」

しばらく使っていると、別の困りごとが出てきました。ページがたまってくると、「このセッション、どこまで進んでいたっけ」が分からなくなるのです。確かめるには、ページを 1 枚ずつ開いて読み返すしかありません。

そこで、ページを書くたびに、セッション全体の「現在の状況」と「次やること」も Claude Code に言い直してもらい、セッションのトップに出すようにしました。

![セッションのトップには「現在の状況」と「次やること」](/images/2026-09-24-cc-pages-concept/status.png)

前回からの差分ではなく、毎回まるごと書き直してもらうのがポイントです。古い項目が消し忘れで残り続けることがなく、頼み方もずっと単純で済みます。

## おわりに

やっていることは、ターミナルの外に「読む場所」を 1 つ足しただけです。仕組みそのものは単純で、大事なのはむしろ、ターミナルに何を残すか、いつページにするか、という決めごとの方でした。

ちなみにこの記事の構成も、Claude Code にページで出してもらいながら練りました。Claude Code の長い回答に目が滑っている人の参考になれば嬉しいです。
